# Quickwit Object Storage Architecture

SoonWhy uses Quickwit as the telemetry search and indexing layer, with R2/S3-compatible object storage as the durable index store.

    OpenTelemetry
         |
         v
    OTLP ingestion
         |
         v
    NATS JetStream
         |
         v
    Quickwit indexers
         |
         v
    R2 / S3-compatible object storage
         |
         +------------------+
         |                  |
         v                  v
    Quickwit searchers   Analysis engine
         |                  |
         +--------+---------+
                  v
            Evidence / RCA

Quickwit owns the searchable telemetry index. Its splits are stored directly in object storage.

Telemetry is separated into logs, traces, requests, and metrics indexes. Every document carries org_id and project_id, which are used as tenant filters and Quickwit tag fields.

NATS remains the durable ingestion boundary. It decouples OTLP receipt from indexing and provides the retry/DLQ boundary.

## Object storage

Configure Quickwit with:

- QW_DEFAULT_INDEX_ROOT_URI=s3://<bucket>/quickwit
- QW_METASTORE_URI=s3://<bucket>/quickwit-metastore
- QW_S3_ENDPOINT=<R2 S3 endpoint>
- AWS_ACCESS_KEY_ID=<R2 access key>
- AWS_SECRET_ACCESS_KEY=<R2 secret>

For local development, the same configuration can point at MinIO.

## Tenant isolation

Every search generated by the API includes organization and project predicates. Resource IDs are never the only telemetry boundary.

The organization remains the SaaS security boundary. Project remains the telemetry boundary inside an organization.

## Detection boundary

The detection and evidence layers build on the Quickwit telemetry boundary. Postgres remains the source of truth for SaaS resources such as organizations, projects, members, and API keys.
